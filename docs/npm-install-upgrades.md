# Deprecated Dependencies and Upgrade Paths

## Suggested Upgrade Path Order
1. `@npmcli/move-file@2.x` → `@npmcli/fs`
2. `npmlog@6.x` → `proc-log` (or “remove by upgrading the toolchain that pulls it in”)
3. `gauge@4.x` → *(remove; if you truly need a CLI progress bar, use something like `cli-progress`)*
4. `are-we-there-yet@3.x` → *(remove; no maintained replacement)*
5. `inflight@1.x` → *(remove; typically disappears when you upgrade `glob`)*
6. `rimraf@3.x` → `rimraf@^4` (or latest)
7. `boolean@3.x` → `yn` *(or replace with a tiny local helper function)*
8. `glob@7.x/8.x` → `glob@^9` (or latest)
9. `@material/mwc-* @0.27.0` → `@material/web`

The npm warning suggests using **`lru-cache`** for similar functionality:contentReference[oaicite:0]{index=0}:contentReference[oaicite:1]{index=1}. - **Code Changes in Qortal UI:** Qortal UI does not directly depend on **inflight** (it was pulled in via old versions of **glob**). After upgrading **glob** (see below), **inflight** will no longer be installed. No changes in Qortal’s own code are needed unless there was custom use of **inflight**. If any custom usage exists (unlikely), refactor it to use an alternative approach (e.g. use an **LRU cache** to manage duplicate async calls, as recommended:contentReference[oaicite:5]{index=5}).

## **rimraf** (v3.0.2 – deprecated; requires v4+)
- **Replacement/Alternative:** **`rimraf`** is still the correct package for deep file deletion, but versions **prior to 4.0.0** are deprecated:contentReference[oaicite:17]{index=17}. The supported replacement is **rimraf v4** or newer, which internally uses Node’s `fs.rm` when available and has dropped old dependencies.
- **Minimum Supported Version:** **4.0.0** is the minimum rimraf version that avoids deprecation (v4+ are supported):contentReference[oaicite:18]{index=18}:contentReference[oaicite:19]{index=19}.
- **Latest Compatible Version:** The latest rimraf is currently 6.x:contentReference[oaicite:20]{index=20}. Upgrading to the newest v6 is ideal, as it includes all fixes – rimraf v5 and v6 mainly added features and Node compatibility, not breaking the basic API. Since Qortal UI targets Node 20, rimraf v6 should work. However, note that rimraf 4+ made a change regarding globbing patterns (see below), which affects all later versions equally. So upgrading straight to v6.1.2 (latest) is fine as long as the glob usage is accounted for.
- **Code Changes in Qortal UI:** If Qortal’s build or npm scripts use **rimraf** with wildcard patterns, a small change is needed. **Rimraf v4** removed automatic glob support by default (it was re-added behind a flag in v4.1+). For example, a script like `rimraf dist/*` will error out in v4+. The fix is to use the `--glob` option in the rimraf CLI or set the `glob: true` option in its API:contentReference[oaicite:21]{index=21}:contentReference[oaicite:22]{index=22}. In Qortal UI, check the build scripts/package.json for any rimraf usage:
  - For **npm scripts** (CLI usage), append `--glob` to the command (e.g. `"clean": "rimraf --glob dist/**"`).
  - For **Node scripts** (JS API), pass the glob option, e.g. `rimrafSync("dist/**", { glob: true })`.
  Other than globbing, rimraf’s API remains the same. If Qortal UI only uses rimraf to remove fixed directories (no wildcards), no code changes are required – just update the version in package.json/devDependencies. After upgrading to rimraf ≥4, the deprecation warning will disappear:contentReference[oaicite:23]{index=23}.

## **glob** (v7.2.3 / v8.1.0 – deprecated; requires v9+)
- **Replacement/Alternative:** Continue using **`glob`** but upgrade to a newer major version. **Glob v9** and above are the supported versions (they removed deprecated dependencies and old Node support):contentReference[oaicite:24]{index=24}:contentReference[oaicite:25]{index=25}. There is no separate package to replace glob; instead, use the latest glob module.
- **Minimum Supported Version:** **9.0.0** is the first non-deprecated version (Glob v9+):contentReference[oaicite:26]{index=26}:contentReference[oaicite:27]{index=27}. Upgrading from 7.x/8.x to 9.x removes the reliance on inflight and other issues. Note that glob v9 targets newer Node versions (dropping support for Node 12/14).
- **Latest Compatible Version:** The glob library is currently at v13 (with v11 being a recent stable before some vulnerability patches):contentReference[oaicite:28]{index=28}:contentReference[oaicite:29]{index=29}. It is recommended to use at least **glob v10 or v11**, which are stable and include important fixes. Glob v12/v13 introduced further changes mainly to remove a vulnerable optional feature (the CLI command execution):contentReference[oaicite:30]{index=30}. Qortal UI, running on Node 20, can adopt the latest glob v13.0.0 for maximum longevity:contentReference[oaicite:31]{index=31}. However, upgrading from v8 to v10+ may require minor code updates as described below.
- **Code Changes in Qortal UI:** If Qortal UI’s code (or build scripts) calls **glob** functions, you may need to adjust for glob’s breaking changes in v9+. In particular, **glob v9** changed its default export and methods:
  - The old usage `const glob = require('glob'); glob.sync(pattern)` no longer works as-is, because glob v9+ uses an ES Module structure and the synchronous API is accessed differently:contentReference[oaicite:32]{index=32}. The fix is to import the `glob` function or use the new `Glob` class. For example, in CommonJS: `const { globSync } = require("glob"); globSync(pattern)` replaces `glob.sync(pattern)`. In ESM: `import { globSync } from "glob";`.
  - Ensure that any **callbacks or promises** usage align with the new API (glob v9+ returns a Promise if you use it as a function without callback).
  In summary, search the Qortal UI code for any `glob(...` or `glob.sync` usage and update it to the new interface. If Qortal’s build process uses glob indirectly (e.g. via other tools or only in CLI form), you might not need direct changes aside from bumping the version. After upgrading to glob ≥9, the deprecation warnings for glob (and its old deps like inflight) will be resolved:contentReference[oaicite:33]{index=33}.

## **Material Web Components (MWC) – @material/mwc-* (v0.27.0, deprecated)**
*Applies to the following packages, all at 0.27.0:* `@material/mwc-button`, `mwc-textfield`, `mwc-checkbox`, `mwc-radio`, `mwc-fab`, `mwc-icon-button`, `mwc-icon`, `mwc-line-ripple`, `mwc-floating-label`, `mwc-notched-outline`, `mwc-formfield`, `mwc-snackbar`, `mwc-dialog`, `mwc-drawer`, `mwc-tab-bar`, `mwc-tab`, `mwc-tab-scroller`, `mwc-tab-indicator`, `mwc-menu`, `mwc-select`, `mwc-slider`, `mwc-list`, `mwc-base`, `mwc-ripple` – **all are part of the MWC beta library.**
- **Replacement/Alternative:** Google’s **Material Web Components (MWC)** in beta (v0.27.0) are no longer supported. The official path forward is to migrate to the **Material Web** library (sometimes called “Material 3 Web Components”), provided by the **`@material/web`** package:contentReference[oaicite:34]{index=34}. In other words, the MWC package line has been succeeded by a new set of components in `@material/web` which corresponds to the latest Material Design spec. (Google has put MWC in maintenance mode and directs users to switch to the new library:contentReference[oaicite:36]{index=36}.)
- **Minimum Supported Version:** There is **no newer MWC version** beyond 0.27.0 – the beta was the last. To avoid using deprecated components, you must upgrade to the **Material Web** package. The equivalent components in **`@material/web`** reached stable status around version 1.0 (and are now in 2.x). Thus, the “minimum” supported version is effectively **@material/web 1.0.0** (or whatever version contains the needed components) since any 0.xx MWC is deprecated.
- **Latest Compatible Version:** You should upgrade to the latest **@material/web** release (currently ~**v2.4** in late 2025:contentReference[oaicite:37]{index=37}). This ensures you get all current Material Design 3 components and bug fixes. The Material Web package is evolving, but since Qortal UI is being updated from a very old MWC beta, it’s advisable to go straight to the newest version. Note that Material Web 2.x may include design changes (Material You styling) that differ from the old Material Design 2 look – which is expected as part of the update.
- **Code Changes in Qortal UI:** Migrating from MWC 0.27 to **Material Web (@material/web)** will require changes in imports and possibly component usage:
  - **Imports:** Instead of importing from `@material/mwc-...`, you will import modules from `@material/web`. For example, replace `import '@material/mwc-button';` with an import from the Material Web package. The exact import path depends on the component – Material Web exports sub-packages for components. For instance, you might use `import { MdFilledButton } from "@material/web/button/filled-button.js";` and then use `<md-filled-button>` in HTML. (Material Web components often have an `Md*` class and `<md-*>` tag naming for Material 3.) Consult the Material Web documentation for each component’s new import path and tag name.
  - **Component API:** The general functionality of buttons, textfields, checkboxes, etc., remains similar, but some APIs have changed. For example, Material Web might have different property names or styling custom properties. You should review the release notes for each component or the official upgrade guide (if available). As a concrete example, the MWC `<mwc-button>` becomes a Material Web `<md-filled-button>` or `<md-outlined-button>` depending on variant; attributes like `raised`/`outlined` might be handled by choosing a specific element class rather than boolean attributes.
  - **Styling:** Material Web components use the new MD3 styles. Custom CSS custom properties (design tokens) and the way to include the theme might differ. You might need to adjust CSS variables or Sass mixins if Qortal UI customized the look of MWC components. For instance, the old `--mdc-theme-primary` etc. tokens are likely similar, but double-check any theme overrides.
  - **Formfield and others:** Some components (e.g., `<mwc-formfield>`, `<mwc-line-ripple>`) in 0.27.0 were for internal composition. Material Web may have integrated or changed these. You might not need to manually use `<mwc-line-ripple>` or `<mwc-floating-label>` anymore, as the new textfield component includes its own ripple/label internally. So usage of those low-level components can be removed in favor of the higher-level component.
  
  Overall, expect a moderate refactor: update all references to MWC components in Qortal UI’s HTML/JSX/TSX files to use the new Material Web components, and adjust event names or properties if they changed. This is likely the most invasive upgrade in the list, but it is necessary since the old MWC beta will no longer receive fixes:contentReference[oaicite:38]{index=38}. After migrating, Qortal UI will be on supported Material Design components moving forward.

## **boolean** (v3.2.0 – deprecated)
- **Replacement/Alternative:** The **`boolean`** package (from **thenativeweb** library) is no longer supported:contentReference[oaicite:44]{index=44}. There is no official direct replacement, but the functionality is simple: it converts strings like "true"/"false", "yes"/"no", etc., to actual booleans:contentReference[oaicite:45]{index=45}:contentReference[oaicite:46]{index=46}. Since it’s a light utility, you can replace it with a few lines of code or another small library. For example, the **`yn`** package is a well-maintained alternative that parses yes/no true/false strings to boolean values (it covers 'y/n', 'yes/no', 'true/false', '1/0', 'on/off' etc., similar to boolean’s behavior). Alternatively, you can implement a custom helper to handle the specific strings Qortal needs to interpret as booleans.
- **Minimum Supported Version:** *None.* The last published version 3.2.0 is deprecated and there is no newer version (the npm registry entry was deprecated entirely):contentReference[oaicite:47]{index=47}.
- **Latest Compatible Version:** Not applicable – the solution is to remove the dependency. If the Qortal UI code needs this functionality, use a different approach as mentioned. For instance, **yn@4** (latest) could be used if you want an off-the-shelf solution.
- **Code Changes in Qortal UI:** You should identify where **boolean** is used in the code. Commonly, developers used it to convert environment variables or config strings to booleans. In Qortal UI, search for `require('boolean')` or `boolean(`. Once found, replace those calls with an alternative:
  - If using **`yn`**: e.g. replace `boolean(myVar)` with `yn(myVar, { default: false })` or similar (depending on how you want to handle undefined and what default is needed).
  - Or implement a small function: e.g. 
    ```js
    function toBoolean(val) {
      if (val === true || val === false) return val;
      if (typeof val === 'string') {
        const normalized = val.trim().toLowerCase();
        return ['true','t','yes','y','on','1'].includes(normalized);
      }
      return false;
    }
    ```
    (and expand it to handle “false/off/0” as needed for your case).
  
  After removing **boolean** and adjusting the code, run tests to ensure the logic still works for all expected inputs. This will eliminate the warning and remove an unmaintained package from your project.
