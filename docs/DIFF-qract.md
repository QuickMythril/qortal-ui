## qortalRequest: Core vs Hub vs UI

- **Coverage**: Core exposes 30+ actions (names, QDN search/fetch/publish, wallet/payments, chat, groups, ATs, blocks/tx, lists). Hub handles all interactive publish/wallet/chat/group/poll/admin flows and adds name trading/foreign-server helpers but omits handlers for read-only Core actions (still serviced in-page by `q-apps.js`). UI handles a smaller interactive subset (publish/crypto/chat/polls/trade bot/wallet/admin) and lacks name trading and group-admin actions advertised by Hub.
- **Name lookups**: Core/Hub (via Core HTTP) return NameSummary objects for `GET_ACCOUNT_NAMES`; UI overrides and returns a string array, moving the active name to index 0 for the logged-in user. `GET_PRIMARY_NAME` is absent in Core, string-valued in Hub/UI (Hub fetches `/names/primary`, UI uses Redux fallback for self), so apps expecting NameSummary must adapt per host.
- **Chat send**: Core expects PoW difficulty 8 (balance ≥4 QORT) or 18 (<4 QORT), 4KB cap, direct messages require recipient public key; group messages unencrypted. Hub enforces balance ≥4 QORT and always uses difficulty 8, blocking low-balance sends; UI allows low balances but raises difficulty to 18. Both support `fullMessageObject/fullContent` and optional `chatReference`; neither encrypts group payloads.
- **Action gaps in UI**: Missing `REGISTER_NAME/UPDATE_NAME/BUY_NAME/SELL_NAME/CANCEL_SELL_NAME`, group admin actions (`INVITE/KICK/BAN/ADD_ADMIN/...`), and Hub’s extra payments (`MULTI_ASSET_PAYMENT_WITH_PRIVATE_DATA`, `TRANSFER_ASSET`, `SIGN_FOREIGN_FEES`). Apps relying on these will work in Hub but not in the current UI.
- **Additional host-only actions**: Hub adds foreign-server management, PDF viewer, name trading; UI adds friends/profile/notification helpers. Neither host implements Core’s read-only actions in their listeners because those are serviced by `q-apps.js` directly against the node.
